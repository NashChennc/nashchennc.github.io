MFU 模型浮点数利用率

在训练大规模语言模型（LLM）时，MFU（Model FLOPs Utilization，模型算力利用率） 通常只能达到 40% 到 60%（即 0.5 左右），这在工业界和学术界确实是一个普遍现象（例如 PaLM、LLaMA 的技术报告中，MFU 大多在 45%~55% 之间）。

MFU 定义为：模型理论上所需的浮点运算次数 / (GPU 峰值算力 × 训练时间)。

为什么极其昂贵的 GPU 集群，有一半的算力被“浪费”了？这主要是由存储墙、分布式通信、重计算机制以及算子特性共同决定的。具体可以拆解为以下四个核心原因：

1. 内存墙与算术强度不足（Memory Wall & Arithmetic Intensity）

GPU 算力的增长速度远快于显存带宽（HBM）的增长速度。评估一个操作能否跑满算力的关键指标是算术强度（Arithmetic Intensity），即“每读取 1 Byte 数据，能执行多少次浮点运算”。

  • 高算术强度算子：稠密矩阵乘法（Dense GEMM），比如 Linear 层。这类算子可以把 Tensor Core 喂饱。

  • 低算术强度算子（Memory-bound）：LayerNorm、Softmax、Activation（如 SwiGLU）、Dropout 等逐元素（Element-wise）操作。这些操作的特点是计算极少，但需要频繁读写显存。

    在执行这些操作时，Tensor Core 大部分时间在“饿肚子”等待数据从 HBM 搬运过来。虽然它们在模型总 FLOPs 中占比极小，但在时间开销上往往占据 20% 甚至更高。这也是为什么后来出现了 FlashAttention 等技术，核心思想就是通过算子融合（Kernel Fusion）减少中间变量的显存读写，从而提升 MFU。

2. MFU 与 HFU 的差异：激活重计算（Activation Recomputation）

在大模型训练中，为了节省显存（防止 OOM），通常会使用 梯度检查点（Gradient Checkpointing / 激活重计算） 技术。即在前向传播时不保存部分中间激活值，而在反向传播时重新计算它们。

  • HFU（硬件算力利用率）：衡量 GPU 实际执行的算力。重计算产生的 FLOPs 会被算进去。

  • MFU（模型算力利用率）：只计算一次理想前向 + 一次理想反向的理论 FLOPs。

因为重计算的存在，GPU 实际上多做了大约 33% 的额外计算。这意味着，即便 GPU 硬件在那一刻全速运转（HFU 可能高达 60-70%），但因为多做的这些计算对模型本身推进 step 是“无用功”，所以在计算 MFU 时，分母（时间）变大了，分子（理论 FLOPs）没变，导致最终算出来的 MFU 降低。

3. 分布式通信的开销（Communication Overhead）

千亿参数模型通常需要 3D 并行（数据并行 DP + 张量并行 TP + 流水线并行 PP），这引入了巨大的跨 GPU 和跨节点通信开销：

  • 张量并行（TP）：在前向和反向中需要频繁执行 All-Reduce。虽然可以通过 NVLink 高速互联，但每次通信都会打断连续的矩阵乘法，导致计算流线停顿。

  • 流水线并行（PP）：会产生不可避免的流水线气泡（Pipeline Bubbles）。在每个 Batch 的开头和结尾，总有部分 GPU 处于空闲等待状态，无法执行计算。

  • 数据并行（DP / ZeRO）：在反向传播结束时需要 All-Gather 收集参数或 Reduce-Scatter 规约梯度（受限于 InfiniBand 网络带宽）。

    虽然可以通过计算与通信重叠（Overlap）来掩盖部分开销，但在实际工程中很难做到 100% 完美隐藏。

4. 并非所有运算都能使用 Tensor Core

现代 GPU 标称的“峰值算力”（如 A100 的 312 TFLOPS）是基于 FP16/BF16 的 Tensor Core 算力。

但模型中并非所有操作都能交给 Tensor Core 处理。例如：

  • 优化器状态更新（Adam）通常需要在 FP32 下进行，依赖 CUDA Core。

  • 许多底层数据格式转换、Mask 生成、张量拼接（Concat/Split）都是非张量核心操作。

    当你使用单精度或非矩阵运算时，GPU 实际能达到的物理算力上限本来就远低于标称的 Tensor Core 峰值。

总结

MFU 约等于 0.5 并非算法写得烂，而是系统工程的一种物理极限妥协。在真实的 Roofline 模型下，通信延迟、访存带宽瓶颈以及节省显存的妥协（重计算），共同构成了那“丢失的 50%”。对于 AI 系统的底层优化（比如算子融合、拓扑感知的通信调度、更优的 ZeRO 策略），其本质目标就是将这个 0.5 努力向 0.55 或 0.6 推进。

稀疏利用率

你提到的“在稠密矩阵上算力要除以 2”，通常是指在查阅 NVIDIA GPU 算力规格表（Spec Sheet）时，官方标称的峰值算力（Peak TFLOPS）在跑标准的稠密矩阵乘法（Dense GEMM）时需要减半计算。

这背后主要有两个层面的原因：一个是硬件架构与商业宣传的原因（最常见），另一个是算法层面上 FLOPs 与 MACs 的统一定义问题。

1. 硬件层面：NVIDIA 的 2:4 结构化稀疏（Structured Sparsity）

从 Ampere 架构（A100、RTX 30 系列）开始，NVIDIA 在 Tensor Core 中引入了 2:4 结构化稀疏（2:4 Fine-Grained Structured Sparsity） 的特性，并在后续的 Hopper（H100）和 Ada Lovelace 架构中延续。

  • 它的原理是：在神经网络的权重矩阵中，如果在每 4 个连续的元素中，有至少 2 个元素是 0（即 50% 的特定稀疏度），Tensor Core 就可以通过硬件级的压缩，直接跳过这些 0 的计算。

  • 带来的结果：原本需要 2 个时钟周期算完的矩阵块，现在 1 个周期就能算完。这使得 GPU 在处理这种特定稀疏矩阵时，吞吐量（算力）直接翻倍。

为什么稠密矩阵要除以 2？

为了让纸面数据更好看，NVIDIA 在发布会的 PPT 和官方规格表中，通常把这个翻倍后的“稀疏算力（Sparse TFLOPS）”作为头条宣发数据。

例如，H100 PCIe 版本的 FP16 Tensor Core 算力标称为 1513 TFLOPS。但这个数字是基于 2:4 稀疏特性的。如果你的模型是标准的稠密矩阵（Dense Matrix）——即没有任何结构化剪枝，所有的参数都需要参与计算——Tensor Core 无法触发跳过 0 的优化，实际的峰值算力就会回落到物理硬件的真实吞吐上限，也就是标称数字的一半：1513 / 2 ≈ 756 TFLOPS。

2. 算法层面：FMA 指令中的 FLOPs 与 MACs

如果你的语境不是在看 GPU 硬件规格，而是在手算模型的理论计算量，那么“除以 2”通常和乘加操作（MAC）与浮点运算（FLOP）的换算有关。

在稠密矩阵乘法（比如 $C = A \times B$）或全连接层中，最核心的操作是点积。点积的基本单元是 $a \times b + c$，也就是一次乘法加上一次加法。

  • MAC（Multiply-Accumulate）：乘法和加法被视为1 个不可分割的乘加操作。

  • FLOPs（Floating Point Operations）：乘法是 1 次浮点运算，加法是另 1 次浮点运算，所以 1 个 MAC 算作2 个 FLOPs。

现代 GPU 都有 FMA（融合乘加，Fused Multiply-Add） 指令，可以在一个时钟周期内同时完成乘和加。

当你评估一个稠密矩阵乘法所需的硬件算力时，通常公式是：

$$ \text{实际所需硬件算力 (FLOPS)} = \text{算法的 MACs 数量} \times 2 $$

反过来说，如果你知道 GPU 每秒能执行多少次浮点运算（FLOPS），那么它每秒能执行的真实矩阵点积次数（MACs）就得 除以 2。

总结来说：

如果你在看显卡算力表，看到诸如“FP16 Tensor Core 算力 1000 TFLOPS”并被告诫在稠密矩阵下要除以 2，那是因为官方给的是 2:4 稀疏化算力，稠密网络吃不到这个翻倍红利；

如果你在算前向传播的计算密度，除以 2 则是为了在 FLOPs（浮点操作数）和 MACs（乘加次数） 之间做单位换算。
