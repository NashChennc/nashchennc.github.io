1. Harness Design Patterns

与早期的 Agent 框架“Agent = LLM + Memory + 工具 + 规划 + 行动”相比，如今的代理工程还包含了工作流设计（例如循环工程）、评估、权限控制和持久状态管理。它不再仅仅是提示模板，而是更接近运行时和软件系统设计：模型如何观察、行动、记忆、自我检查和改进。编码代理产品已经说明，同一个基础模型在不同 harness 下可能表现出显著不同的实际能力。

harness 应当保持简单、通用和可组合。一个过度依赖任务特定启发式规则的 harness，可能在单一 benchmark 上获得收益，却难以迁移。

harness 可以定义为：围绕基础模型、负责组织模型执行的系统层。更接近 agent runtime、工作流引擎和操作系统的组合。

它决定模型如何：

  • 思考、规划和分解任务；
  • 调用工具、执行动作并读取返回结果；
  • 感知、选择、压缩和维护上下文；
  • 保存文件、代码、日志和其他持久化产物；
  • 启动子代理和后台任务；
  • 检查、测试和评价自己的输出；
  • 处理权限、失败、重试、回滚与停止条件。

Pattern 1：Workflow Automation

自动化首先需要给模型一个可以持续运行、测试和迭代的工作流。最典型的是目标驱动循环：Plan → Execute → Observe/Test → Improve → Execute Again 。循环持续到目标达到、预算耗尽或触发停止条件。

Pattern 2：File System as Persistent Memory

长时程代理产生的状态远超单个上下文窗口可以稳定承载的范围。harness 不应把完整工作流、全部轨迹和所有工具返回不断追加到 prompt。更自然的做法是把文件系统作为持久记忆层。

模型当前上下文只包含当前任务需要的信息，而完整历史保存在文件中。模型通过 ls、grep、cat、read、write、edit 等操作按需访问。读写文件和使用 shell 已经是模型在预训练数据中大量接触的操作。因此，相比设计复杂且专用的向量记忆机制，文件系统能够直接利用基础模型已有的软件工程能力。目录、Markdown、JSON、数据库、代码、日志和模型检查点都可以成为持久状态，只要模型能够稳定访问和修改。

Pattern 3：Sub-agent and Backend Jobs

主代理可以生成多个子代理并行处理不同任务，也可以启动后台进程运行耗时实验。核心思想是包括：把容易污染主上下文的局部任务隔离出去；在主代理继续规划时运行训练、构建或数据处理任务。

并行性必须是显式且可检查的。子代理输出若只存在于短暂对话中，很快会变得不可见或过时。若输出保存为文件、日志和状态记录，主代理就能够在中断后恢复，并在之后重新分析整个执行历史。

Coding Agent

Claude Code、Codex、OpenCode 和 Cursor 风格编码代理的核心接口已经逐渐趋同。编码代理通常获得类似 IDE 和终端的工具集合：

编码 harness 的价值不仅是“给模型终端”。它还要决定：

  • 模型每轮看到哪些仓库信息；
  • 是否先搜索再编辑；
  • 怎样限制可修改目录；
  • 如何运行测试；
  • 测试失败后是否回退；
  • 如何避免模型只修改测试来获得通过；
  • 何时压缩上下文；
  • 如何把未完成状态写入文件；
  • 如何控制 token、时间和执行预算。

2. Harness Layer vs. Core Intelligence

第一，近期 harness engineering 会走向 meta-methodology。

优化目标不再只是当前答案，而是产生更好答案的方法本身。例如：

  • 不只修改提示词，而是修改提示词生成器；
  • 不只优化一次工作流，而是优化工作流搜索算法；
  • 不只更新记忆内容，而是更新记忆维护机制；
  • 不只修改 harness，而是修改 harness optimizer。

随着系统演进，手写启发式规则应逐渐减少，通用搜索、学习和评价机制应占据更大比例。

第二，成熟 harness 与更强基础模型会相互促进。

  • 成熟 harness 可以组织自动研究，为模型改进产生代码、实验、数据和方法；
  • 更强模型可以减少 harness 中的脆弱补丁和过度工程，使系统更简单、更可持续；
  • 部分 harness 技巧最终可能被模型训练内化，但外部工具、目标、约束和评价接口仍然会存在。

类比于 prompt engineering：早期大量手工提示技巧随着指令微调和推理能力增强而不再关键，但目标说明、约束、上下文和评价标准并没有消失。

最狭义的 RSI ：模型直接修改自己的参数或认知结构； 更现实、更宽泛的 RSI：包括模型利用当前能力改进训练流水线、数据生成方式、评估器、部署系统和研究流程，由这些系统生产出更强的后继模型。

因此，自我改进不必一开始就表现为“模型直接重写自己的权重”。一个更可能在近期发生的路径是：

  1. 模型先改进自己所处的外部执行系统。
  2. 更好的执行系统让模型能够完成更长、更复杂、更可靠的研究和工程任务。
  3. 这些任务产生更好的数据、训练方法、模型架构或评估方法。
  4. 改进后的模型又获得更强的 harness 设计和优化能力。
  5. 模型能力与 harness 能力形成相互促进的循环。

3. 优化对象的逐级上移

总体演进路线是：

Instruction Prompt → Structured Context → Workflow → Harness Code → Optimizer Code

其含义是：

  1. 最初只优化一段指令文本。
  2. 随后优化包含规则、记忆、示例和证据的结构化上下文。
  3. 再进一步优化模型调用、工具、角色和控制流组成的工作流。
  4. 然后把整个 harness 表示为代码，在更大设计空间中搜索。
  5. 最终连“怎样搜索和修改 harness”的优化器本身也成为优化对象。

模型越强，就越可能处理更复杂、更通用的元级优化目标。

4. Context Engineering

随着智能体任务范围的显著扩大，简单地将所有工具响应和模型生成结果添加到上下文中，很快就会变得难以控制。上下文管理层旨在为长上下文模型 (LLM) 构建一个更结构化、更简洁的上下文，并管理持久状态。毫无疑问，长上下文研究将持续取得进展，但目前长上下文智能和上下文工程有时会相互交织。

长上下文模型与 context engineering 并不是互相替代。更长的窗口提高可访问容量，而 context engineering 决定哪些信息值得进入窗口、以什么结构出现以及如何更新。

-1. 相关工作

ACE：把 Context 视为持续演化的 Playbook

ACE 不把 context 当成不断变长的 prompt，而是当成由结构化条目组成、可以持续更新的 playbook。

系统包含三个角色：

  1. Generator
    根据当前 playbook 执行任务并产生轨迹。轨迹中的决策可以引用具体 playbook 条目。

  2. Reflector
    分析成功和失败轨迹，提炼哪些规则有效、哪些规则有问题以及出现了哪些新经验。

  3. Curator
    将反思结果变成带唯一标识符的结构化条目，并增量更新 playbook。

ACE 的关键设计是避免每轮重写完整 prompt。完整重写容易出现：

  • brevity bias：模型为了写得简洁而删除有用细节；
  • context collapse：经过多轮总结，原始经验逐渐消失或被错误改写。

因此，Curator 输出的是 (identifier, description) 形式的条目，随后通过确定性逻辑进行合并。系统可以周期性去重和精炼，但不会在每轮重新生成全部内容。

  • 【2025-10-06】【Stanford / SambaNova】【ICLR 2026】Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models 提出 ACE，将系统提示、代理记忆和领域策略统一表示为可演化 playbook。实验覆盖离线 context 优化和在线 agent memory，显示增量结构化更新可以降低适配延迟和 rollout 成本，并缓解长时程自我改写中的信息坍缩。

MCE：同时优化 Context 和管理 Context 的 Skill

原文认为，ACE 虽然能从 rollout 中学习经验，但 Generator—Reflector—Curator 流程及条目结构仍由人手工规定。

Meta Context Engineering，MCE，进一步把两个层级分开：

  • 基础层优化“上下文中具体有什么”；
  • 元层优化“应当怎样构造、搜索、过滤和维护上下文”。

一个 skill s 定义 context function：

c_s = (ρ_s, F_s)

其中：

  • ρ_s = {ρ_1, …, ρ_m} 是静态组件，如 prompts、知识库、代码库；
  • F_s = {F_1, …, F_k} 是动态操作，如搜索、选择、过滤和格式化。

双层优化目标为：

Inner: c_s* = argmax J_train(c_s; s)

Outer: s* = argmax J_val(c_s*)

内层寻找在当前 skill 下表现最好的 context；外层在验证集上寻找能够产生更好 context 的 skill。

系统维护历史数据库：

H_(k-1) = {(s_i, c_i, J_i^train, J_i^val)}_(i=1)^(k-1)

元代理读取过去的 skills、context functions 和评估结果，通过 agentic crossover 生成新 skill。基础层 context engineer 执行该 skill，并根据 rollout 反馈继续修改 context。

MCE 不强制 context 必须是固定 bullet schema。一个 context function 可以实现为独立目录，其中包括：

  • skill.md
  • 静态知识文件
  • 动态 context 文件
  • rollout 数据
  • 辅助代码

两个层级都在标准 coding environment 中执行，使用 Read、Write、Edit、Bash、Glob、Grep 和 TodoWrite 等工具。

  • 【2026-01-29】【PKU State Key Lab of General AI】【arXiv 预印本】Meta Context Engineering via Agentic Skill Evolution 提出双层 context engineering。元层使用历史技能的执行和评价记录演化新的 context-management skill，基础层执行 skill 并将 context 优化为自由形式的文件和代码。论文报告在五类领域中相对已有 agentic context engineering 方法取得持续提升。

Meta-Harness：直接搜索决定信息处理方式的代码

Meta-Harness 将优化目标再推进一层：不只优化 context 内容或 context skill，而是优化决定“存什么、取什么、怎样呈现”的完整 harness 代码。

其外循环 proposer 本身是编码代理。整个历史通过文件系统提供，包括：

  • 候选 harness 的源代码；
  • 每个候选的评价分数；
  • rollout 轨迹；
  • 状态更新；
  • 失败记录；
  • 过去候选之间的关系。

编码代理不需要把全部历史塞进一个 prompt，而是使用 grep、cat 等命令主动搜索。

每个候选 harness 是文件系统中的独立目录，包含自己的代码、分数、轨迹和状态。新候选经过执行和评估后，只有满足条件的版本才被保留。最终输出不是单一方案，而是性能、成本等目标下的 Pareto frontier。

原文认为 Meta-Harness 的重要结论不是某个 benchmark 分数，而是：当 harness 被表示为可执行搜索空间时，强编码模型可以进入与人类系统工程师相同的设计空间。

  • 【2026-03-30】【Stanford IRIS Lab / KRAFTON / MIT】【arXiv 预印本】Meta-Harness: End-to-End Optimization of Model Harnesses 使用外层编码代理搜索完整 harness 代码。系统让 proposer 通过文件系统访问所有历史候选的代码、轨迹和分数，而不是将反馈压缩成单段文本。在文本分类、IMO 级数学推理和 TerminalBench-2 编码任务上，搜索得到的 harness 超过多个人工设计基线。

2.3 Workflow Design

2.3.1 专家手工设计的科研工作流

原文先讨论领域专家手工构造的 auto-research pipeline。

科研工作流通常需要覆盖：

  1. 提出研究方向；
  2. 检索和阅读文献；
  3. 形成假设；
  4. 编写代码；
  5. 运行实验；
  6. 分析结果；
  7. 撰写论文；
  8. 执行审稿或质量检查。

这类系统的优势是可以把研究人员的隐性流程和质量标准写入 harness；局限是流程依赖人工设计，可能难以适应新领域。

The AI Scientist

AI Scientist 将研究过程组织为端到端流水线：

  • 从已有研究和模板中生成想法；
  • 评估想法的新颖性；
  • 修改代码并运行实验；
  • 读取实验结果和图表；
  • 撰写论文；
  • 调用自动审稿器进行反馈；
  • 根据评审继续修改。

原文将它视为专家设计 harness 能够协调大部分科研流程的强示范，但同时强调“生成论文”不等于“完成科学发现”。

  • 【2026-06】【Sakana AI / UBC / Oxford】【Nature 2026】Towards End-to-End Automation of AI Research 构建 The AI Scientist，将想法生成、代码实现、实验、结果分析、论文写作和自动评审连接为统一流程。其贡献主要是展示端到端科研自动化的系统工程可行性，而不是证明系统已经具备可靠的科学判断和研究品味。

ScientistOne：把可验证性作为系统中心

ScientistOne 认为，仅评价最终论文是否“像论文”无法发现以下问题：

  • 引用不存在；
  • 报告分数无法复现；
  • 方法描述与代码实现不一致；
  • 实验违反任务规范；
  • 结论没有证据支撑。

因此提出 Chain-of-Evidence，要求每项声明都能够追溯到具体证据：

  • 文献声明对应原始文献；
  • 数值声明对应实验日志；
  • 方法声明对应代码；
  • 结论对应分析和结果。

CoE Audit 进一步执行四类检查：

  1. score verification；
  2. specification violation；
  3. reference verification；
  4. method-code alignment。
  • 【2026-05-25】【Google Cloud AI Research】【arXiv 预印本】ScientistOne: Towards Human-Level Autonomous Research via Chain-of-Evidence 将证据链贯穿文献综述、方案发现和论文写作。论文对五个系统生成的 75 篇论文进行审计，发现所有基线至少存在一种系统性可验证性失败；ScientistOne 在引用真实性、分数验证和方法—代码一致性上显著改善。

Autodata：用 Agent 工作流生成“恰当难度”的数据

Autodata 把数据构造建模为多角色协作流程：

  • Challenger：提出任务；
  • Weak Solver：代表需要被改进的弱模型；
  • Strong Solver：代表更强教师或能力上限；
  • Verifier/Judge：检查题目和答案。

理想样本应位于“强模型能解、弱模型不能解”的难度区间。若两者都能解，样本缺乏训练价值；若两者都不能解，样本可能错误或过难。

Challenger 根据 solver 和 verifier 的反馈持续更新自己的生成策略。

原文指出它与完整 RSI 仍有距离：生成的数据主要用于微调弱 solver，而强 solver 没有在闭环中同步提升。若强模型不随循环进化，该过程更像在自动生成的任务分布上进行间接蒸馏。

  • 【2026-06-24】【Meta FAIR】【arXiv 预印本】Autodata: An Agentic Data Scientist to Create High Quality Synthetic Data 提出 Agentic Self-Instruct，通过 challenger、弱求解器、强求解器和 verifier 构造数据生成闭环，并进一步 meta-optimize 数据科学代理本身，使推理算力可以转化为更高质量的训练和评估数据。

2.3.2 将 Workflow Design 变成搜索问题

原文认为 workflow 的设计空间非常大，包括：

  • 代理数量；
  • 代理角色；
  • prompt；
  • 工具；
  • 调用顺序；
  • 分支条件；
  • 循环结构；
  • 反思和验证步骤；
  • 信息在代理间的传递方式。

因此，不应只依赖人工设计，也可以将 workflow 表示为代码或图，并通过搜索算法自动发现更好的结构。

Self-Refine：生成—反馈—修订的基础单元

Self-Refine 是许多后续工作流中的基础操作：

  1. 模型生成初始答案；
  2. 同一模型评价答案并给出具体反馈；
  3. 模型根据反馈修改答案；
  4. 重复直到达到轮数或停止条件。

这一方法不需要额外训练、监督数据或独立奖励模型。其局限是反馈质量受基础模型能力约束，而且模型可能无法识别自己的深层错误。

  • 【2023-03】【CMU LTI / AI2 / UW / Google Brain / NVIDIA】【NeurIPS 2023】Self-Refine: Iterative Refinement with Self-Feedback 系统化研究同一语言模型执行生成、反馈和修订的迭代流程。该循环后来常被用作更复杂代理搜索系统中的候选检查和局部优化算子。

ADAS：让 Meta-Agent 编写新的代理程序

Automated Design of Agentic Systems，ADAS，将 agent design 本身定义为优化问题。

Meta Agent Search 的基本流程是：

  1. 用 CoT、Self-Refine 等简单代理初始化 archive。
  2. Meta-Agent 阅读 archive 中的已有设计和表现。
  3. Meta-Agent 先提出新工作流的高层描述。
  4. 将工作流实现为可执行代码。
  5. 对草稿执行两轮 Self-Refine，以检查设计质量和新颖性。
  6. 在目标任务上评估候选代理。
  7. 将成功候选加入 archive。
  8. 重复搜索。

由于代理以程序语言表示，理论设计空间可以包含任意 prompt、工具调用、控制流和模块组合，而不仅是预先定义的图模板。

  • 【2024-08-15】【UBC / Vector Institute】【ICLR 2025】Automated Design of Agentic Systems 提出 ADAS 和 Meta Agent Search。元代理基于不断增长的历史 archive 编写新代理程序，候选在代码、科学和数学任务上评估。论文发现自动发现的部分代理设计可跨任务和模型迁移，说明搜索得到的并非完全是 benchmark 特定模板。

AFlow：用 MCTS 搜索工作流图

AFlow 将 workflow 表示为有向图：

  • 节点是调用 LLM 的动作；
  • 边和节点之间的连接逻辑由代码实现；
  • 完整图定义一次代理执行流程。

优化使用 Monte Carlo Tree Search：

  1. 用模板工作流 W_0 初始化搜索树。
  2. 依据候选分数和均匀探索的混合策略选择节点。
  3. 根据当前工作流的评测表现，让 LLM 生成修改版本。
  4. 执行并评价新工作流。
  5. 若候选在预算内带来改善，将其加入树中。
  6. 重复搜索，直到达到预算或 top-k 平均分不再提升。

  • 【2024-10-14】【FoundationAgents / DeepWisdom / HKUST(GZ)】【ICLR 2025 Oral】AFlow: Automating Agentic Workflow Generation 将代理工作流编码为图，并通过 MCTS 在执行反馈下搜索节点和控制流修改。相比只生成完整程序，树搜索能够显式平衡探索与利用，并保留多个潜在工作流分支。
