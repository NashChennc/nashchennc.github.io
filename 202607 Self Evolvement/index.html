202607 Self-Improvement Safety

2.4 Self-Improving Harness

2.4.1 Code 是统一的 Harness 表示语言

Context engineering 和 workflow design 都只覆盖 harness 的一部分。完整 harness 还可能包括：

  • system prompt；
  • tool definitions；
  • tool implementations；
  • middleware；
  • memory；
  • permissions；
  • sub-agent configuration；
  • control flow；
  • evaluator integration；
  • error handling。

原文认为代码是定义这些组件及其关系的通用语言。若 LLM 能够修改执行代理的代码，它可以搜索比自然语言 prompt 更大的空间。

2.4.2 STOP：不优化答案，而是优化“改进答案的程序”

Self-Taught Optimizer，STOP，是早期递归 scaffold 改进的代表。

种子 improver I_0 接收：

  • 初始解 s；
  • 效用函数 u；
  • 黑盒语言模型 M；

并输出改进解：

s' = I(u, s; M)

STOP 的目标不是直接改进 s，而是改进 improver I。

在任务集合 D 上定义 improver 的 meta-utility：

û(I) = (1 / |D|) E_(u,s~D)[u(I(u,s;M))]

随后递归更新：

I_t = I_(t-1)(û, I_(t-1); M)

即上一轮 improver 使用自身作为待改进对象，并以 meta-utility 作为评价函数。

实验中，改进后的 improver 自动发现了多种优化策略：

  • 遗传算法；
  • 分解问题并分别改进；
  • 多臂 prompt bandit；
  • 模拟退火；
  • 调整采样温度；
  • beam search；
  • tree search。

原文将其类比为 harness 优化：工作流和 scaffold 本身可以作为效用函数下的优化对象。

但 STOP 也给出重要警告：GPT-4 驱动的递归改进能提高平均表现，而较弱模型驱动的改进可能使表现下降。递归结构不会凭空创造智能，基础模型必须有能力理解、修改并正确使用优化机制。

  • 【2023-10】【Microsoft Research / Stanford】【COLM 2024】Self-Taught Optimizer (STOP): Recursively Self-Improving Code Generation 将“改进程序”本身作为递归优化对象。结果显示强模型能够发现复杂搜索策略，但弱模型可能在递归过程中退化，说明 harness 自我修改的效果仍由核心模型能力约束。

2.4.3 Harness Updating 与 Harness Benefit 是两种能力

原文进一步引用研究，将 harness evolution 分解为两个轴：

  1. Harness Updating
    模型是否能够生成有用的 harness 修改。

  2. Harness Benefit
    模型是否能够在任务执行中正确利用修改后的 harness。

实验发现，从较小开源模型到前沿闭源模型，生成结构相似的 skill 或 harness 修改并不一定表现出巨大差距；但实际受益能力依赖模型是否能够：

  • 在正确时机调用 skill；
  • 正确遵循长程说明；
  • 在复杂轨迹中维持状态；
  • 根据条件选择合适工具；
  • 将外部结构转化为任务收益。

因此，能写出看似合理的 harness 更新，并不等于能从该更新中获益。

  • 【2026-05】【PSU / UCSC / Amazon / Emory】【arXiv 预印本】Harness Updating Is Not Harness Benefit: Disentangling Evolution Capabilities in Self-Evolving LLM Agents 将 harness 修改能力和 harness 利用能力分开评价。研究观察到 harness updating 在不同规模模型间较平坦，而 harness benefit 呈非单调变化，中等能力模型有时受益最大，部分弱模型不会调用新增能力，强模型则可能本身已具备相似行为。

2.4.4 Self-Harness：提出—评价—接受闭环

Self-Harness 使用同一个模型在当前 harness 下执行任务并提出 harness 修改。

完整循环包含三阶段。

阶段一：Weakness Mining

  • 使用当前 harness h_t 执行任务并收集轨迹。
  • 将失败聚类为 verifier-grounded failure patterns。
  • 不只记录表面错误，如 timeout 或 missing artifact，还要识别不同的因果机制。
  • 失败记录需要包含：
    • 最终 verifier 层面的失败原因；
    • 相关代理行为的因果状态；
    • 轨迹揭示的抽象代理机制。

阶段二：Harness Proposal

同一个模型在 h_t 下作为 proposer，获得受限上下文：

  1. 当前 harness 中允许编辑的部分；
  2. 从评价系统提炼的失败模式；
  3. 应当保留的成功行为；
  4. 过去尝试过的修改摘要。

修改应优先针对：

  • 重复出现的错误；
  • 可以通过 harness 解决的问题；
  • 非任务本身难度导致的问题；
  • 可以通过狭窄修改修复的问题。

候选之间应保持差异和多样性，避免只生成同一修改的措辞变体。

阶段三：Proposal Validation

候选修改在两类数据上进行回归测试：

  • D_in：检查目标弱点是否被修复；
  • D_out：检查是否引入未知回归。

只有同时不损害 held-in 和 held-out 表现的候选才能被接受。接受的修改合并为 h_(t+1)；拒绝修改保留记录，但不改变当前 harness。

原文认为该方法能学到模型特定的 harness 指令，因为不同模型的失败机制不同。

同时，作者提出安全担忧：若一个程序可以修改整个操作系统，抽象边界就会被打破。可编辑表面必须严格限制，权限控制、评估器和安全层应位于自修改循环之外。

  • 【2026-06-08】【Shanghai AI Lab】【arXiv 预印本】Self-Harness: Harnesses That Improve Themselves 通过 weakness mining、bounded proposal 和 held-in/held-out validation 自动更新 harness。在 Terminal-Bench-2 上，不同基础模型学到了针对自身错误的不同 harness 指令，并提高 held-out pass rate。

2.4.5 AHE：以可观测性约束 Harness Evolution

Agentic Harness Engineering，AHE，认为 harness 自我演化的瓶颈不是模型不会写代码，而是系统难以回答：

  • 哪个组件导致了失败；
  • 修改依据是什么；
  • 修改后预期改变什么；
  • 性能提升是否真的来自 harness 修改。

因此提出三个 observability pillars。

1. Component Observability

每个可编辑 harness 组件都在文件系统中有明确表示，使动作空间可见且可追踪。

AHE 将 harness 分为七类组件：

  1. system prompt；
  2. tool description；
  3. tool implementation；
  4. middleware；
  5. skill；
  6. sub-agent configuration；
  7. long-term memory。

每个失败模式应映射到具体组件，从而避免无目标地修改整个系统。

2. Experience Observability

系统将大量原始轨迹压缩为分层证据：

  • 每条轨迹存为独立文件；
  • Agent Debugger 对单任务轨迹分析成功或失败根因；
  • 生成 per-task analysis report；
  • 将任务报告聚合为 benchmark overview；
  • 必要时仍可下钻读取原始轨迹。

这种分层访问比把全部轨迹放入上下文更节省 token，也保留了追溯能力。

3. Decision Observability

每次修改都必须带有可在下一轮检验的预测。

Evolve Agent 读取仓库后选择要修改的组件，并在 manifesto 中记录：

  • 失败证据名称；
  • 推断的根因；
  • 目标修复；
  • 预期修复的行为；
  • 可能出现回归的行为。

系统施加两类关键约束：

  • 修改只能发生在 harness workspace；
  • runs、tracer、verifier 和 LLM configuration 保持只读。

这样可以阻止关闭 verifier、更换模型或增加推理预算等 reward hacking，使性能变化能够归因于 harness 修改。

  • 【2026-04】【Fudan NLP / PKU / Qiji Zhifeng】【arXiv 预印本】Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses 从组件、经验和决策三个层面建立可观测性。论文在 Terminal-Bench-2 上超过多个人工编码 harness，并显示冻结后的已演化 harness 可以迁移到 SWE-bench Verified，说明其可能编码了通用工程经验，而不只是适配单个 benchmark。

2.5 Evolutionary Search

2.5.1 为什么 Harness 适合进化搜索

进化搜索维护候选种群，反复执行：

  1. 选择父代；
  2. 生成变异；
  3. 评价后代；
  4. 保留高 fitness 或高 novelty 候选；
  5. 重复演化。

原文认为它适合以下问题：

  • 搜索空间巨大或形状不规则；
  • 无法方便地求梯度；
  • 但候选解容易自动执行和评价。

Harness 同时包含代码、prompt、workflow 和工具配置，搜索空间离散且复杂，但许多任务可以通过测试或 benchmark 自动评价，因此与进化搜索较匹配。

2.5.2 Promptbreeder：同时演化 Prompt 和 Mutation Prompt

Promptbreeder 不只演化任务 prompt，还演化用于指导模型修改任务 prompt 的 mutation prompt。

这形成自指结构：

  • task prompt 决定模型怎样解决任务；

  • mutation prompt 决定模型怎样改进 task prompt；

  • mutation prompt 本身也可以被变异和选择。

  • 【2023-09】【Google DeepMind】【arXiv 预印本】Promptbreeder: Self-Referential Self-Improvement via Prompt Evolution 使用多类 mutation operator 和种群搜索优化任务 prompt，同时让变异指令共同演化。其重要性在于把“产生改进的方法”纳入搜索，而不只是搜索最终提示词。

2.5.3 Darwin Gödel Machine：让可编辑代理产生后代

DGM 与只优化解决方案的系统不同，它直接演化一个可编辑的 coding-agent harness repository。

基本算法：

  1. 用一个初始编码代理建立种群。
  2. 每轮选择一个父代理。
  3. 选择概率与性能正相关，与已有子代数量负相关，从而兼顾利用和多样性。
  4. 父代理读取自己的 benchmark 日志。
  5. 父代理使用 bash 和 editor 修改自身 harness 代码。
  6. 修改后的版本成为一个新代理分支。
  7. 评价新代理。
  8. 只有表现达到要求的代理进入种群。
  9. 重复直到满足停止条件。

模型权重保持冻结，演化发生在 harness 层。

原文引用的实验中，使用 Claude 3.5 Sonnet 和较简单的初始 harness，DGM 代理在 SWE-bench Verified 上从约 20% 提升到约 50%，在 Polyglot 上从约 14.2% 提升到约 30.7%。

  • 【2025-05】【UBC / Vector Institute / Sakana AI】【arXiv 预印本】Darwin Gödel Machine: Open-Ended Evolution of Self-Improving Agents 构建开放式自修改代理种群。每个代理既是任务求解器，也是可以被其后代继承和修改的程序。通过分支式 archive 避免单一路径退化，并使不同 harness 设计能够长期共存。

2.5.4 AlphaEvolve：冻结模型驱动的程序进化

AlphaEvolve 维护候选程序池，让冻结的 LLM 生成代码 diff。

每轮 prompt 可能包含：

  • 父程序；
  • 父程序的运行结果；
  • 优化目标；
  • 修改说明；
  • 元信息。

编码代理可以访问完整仓库，但可进化区域通过以下标记限制：

  • # EVOLVE-BLOCK-START
  • # EVOLVE-BLOCK-END

这种设计在给予模型足够上下文的同时限制修改表面。

AlphaEvolve 还允许 meta-prompt、说明和上下文与解决方案程序共同演化。消融实验显示，进化流程、上下文、meta-prompt、全文件访问以及更强模型都对最终表现有贡献。

  • 【2025-06】【Google DeepMind】【Google DeepMind 技术报告】AlphaEvolve: A Coding Agent for Scientific and Algorithmic Discovery 将 LLM 代码生成与自动 evaluator、候选数据库和进化选择结合。系统适用于矩阵运算、算法发现和数据中心调度等具有明确可执行评价函数的问题。

2.5.5 GEPA：自然语言反思与 Pareto 进化

GEPA 使用语言模型阅读试错轨迹，并通过自然语言反思诊断：

  • 当前 prompt 的失败原因；
  • 哪些任务已经解决；
  • 哪些策略只对部分任务有效；
  • 怎样修改 prompt；
  • 哪些历史候选包含互补经验。

随后将反思生成的 prompt 更新加入进化搜索。系统维护 Pareto frontier，而不只保留单一平均分最高的候选，从而保留在不同任务子集上表现互补的策略。

  • 【2025-07】【UC Berkeley / Stanford / MIT / Databricks】【arXiv 预印本】GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning 结合轨迹级自然语言反思和遗传—Pareto 搜索，用少量完整 rollout 提取高信息密度反馈。在多个语言模型优化任务中，论文报告其样本效率可以超过若干强化学习方法。

2.5.6 ShinkaEvolve：提高 LLM 程序进化的采样效率

ShinkaEvolve 针对进化搜索计算开销大、候选重复的问题提出三个组件：

  1. Parent Sampling
    综合父代性能排名和已产生后代数量。高性能候选获得更多机会，但不会由少数候选垄断全部预算。

  2. Code-Novelty Rejection Sampling
    使用代码嵌入的余弦相似度检测候选是否与已有种群过于相似，拒绝低新颖性样本。

  3. Meta-Scratchpad
    从成功方案中提炼可复用模式，为未来变异提供指导。

  • 【2025-09】【Sakana AI】【arXiv 预印本】ShinkaEvolve: Towards Open-Ended and Sample-Efficient Program Evolution 通过父代采样、新颖性过滤和元级经验记录，提高 LLM 驱动程序演化的样本效率，并降低种群被近似重复程序占据的风险。

2.5.7 ThetaEvolve、Hyperagents 与 DemoEvolve

  • 【2025-11】【Microsoft Research / UW】【arXiv 预印本】ThetaEvolve: Test-Time Learning on Open Problems 在 AlphaEvolve 风格的候选程序数据库和 in-context evolution 之外加入强化学习。其目标是让模型不仅从当前 prompt 读取成功经验，还能把开放问题求解策略写入权重，实现程序搜索和参数学习结合。

  • 【2026-03】【Meta FAIR / Meta Superintelligence Labs / UBC / Vector Institute】【arXiv 预印本】Hyperagents 在 DGM 的基础上引入 meta-agent。任务代理被表示为可修改程序，meta-agent 决定如何修改已有代理并产生新代理，将自我修改从编码任务扩展到更一般的可计算任务。

  • 【2026-05-23】【Tsinghua / AgiBot】【arXiv 预印本】DemoEvolve: Overcoming Sparse Feedback in Agentic Harness Evolution with Demonstrations 针对长时程任务只有稀疏最终奖励的问题，在自生成 rollout archive 中加入人类专家演示。演示为失败诊断和 harness 修改提供参考轨迹，帮助系统判断问题出现在规划、工具调用还是执行阶段。

2.5.8 进化搜索的适用边界

原文认为，这类方法在以下任务上最有优势：

  • 矩阵乘法；
  • GPU kernel 优化；
  • 算法竞赛；
  • 数据中心调度；
  • 可运行程序优化；
  • 具有自动测试的编码任务。

共同点是 fitness 容易量化。

当评价具有以下特征时，进化搜索会明显变困难：

  • 评价缓慢；
  • 评价成本高；
  • 指标模糊；
  • 多个评价者意见不一致；
  • 只能依赖启发式 judge；
  • 真正价值需要长期才能显现。

此外，进化搜索需要大量候选执行，计算效率和搜索效率仍是核心问题。

2.6 Joint Optimization with Model Weights

2.6.1 从非参数更新走向参数与系统联合更新

Harness evolution 改变的是模型之外的非参数系统。完整自我改进还可以允许模型同步修改权重。

权重更新可以来自：

  • 改进训练数据；
  • 改进训练流水线；
  • SFT；
  • LoRA；
  • 强化学习；
  • 测试时训练；
  • 持续学习。

联合系统必须决定：当前失败应该通过修改 harness 解决，还是通过修改模型参数解决。

例如：

  • 工具说明不清晰，适合修改 harness；
  • 模型缺少领域知识，可能需要权重更新；
  • 工作流缺少验证步骤，适合修改 harness；
  • 模型无法执行已有复杂策略，可能需要训练；
  • 高频重复经验可能适合从 memory 内化到权重。

参考文献补充：Test-Time Discovery

  • 【2026-01】【Stanford / NVIDIA / Together AI / UCSD / Astera Institute】【arXiv 预印本】Learning to Discover at Test Time 提出 TTT-Discover，在面对单个开放问题时继续对模型执行测试时强化学习。与提高任务平均准确率不同，其目标更接近在大量尝试中找到一个突破性最优解，为开放式科学和算法发现提供参数侧自我改进路径。

2.6.2 Continual Harness

Continual Harness 在不重置的长时程游戏环境中同时执行：

  • harness 更新；
  • 轨迹和记忆积累；
  • 策略模型持续学习。

当当前策略产生低奖励轨迹时，强教师模型为轨迹生成更好的动作或标签，随后将这些信息蒸馏到较弱策略模型中。这样，外部 harness 和内部 policy 可以共同适应持续变化的任务。

  • 【2026-05-11】【Princeton / Google DeepMind】【arXiv 预印本】Continual Harness: Online Adaptation for Self-Improving Foundation Agents 在长时程游戏设置中结合 prompt、skill、sub-agent、memory 更新和教师蒸馏，使代理在不中断任务的情况下持续适应。论文强调 online adaptation，而不是在每轮实验后重新初始化代理。

参考文献补充：不确定性引导的测试时发现

  • 【2026-05-11】【Stanford / NUST / OU】【arXiv 预印本】Epistemic Uncertainty for Test-Time Discovery 维护多个 LoRA 假设，以不同适配器在 token 级输出上的分歧估计 epistemic uncertainty。系统将这种分歧作为探索信号，引导模型访问训练覆盖不足、但可能产生新发现的区域。

2.6.3 SIA：由 Feedback-Agent 决定更新 Harness 还是权重

SIA 包含三个主要角色：

  • Meta-Agent：提出初始 harness；
  • Task-Specific Agent：执行实际任务；
  • Feedback-Agent：读取近期轨迹，决定下一轮更新 harness 还是模型权重。

这一结构直接把“更新哪一层”变成代理决策问题。

但原文对当前实验证据持保留态度：

  • Task-Specific Agent 使用的模型明显弱于 Meta-Agent 和 Feedback-Agent；
  • 不同组件使用不同能力模型，难以判断收益来自架构还是强模型辅助；
  • 基线较弱，难以与其他 harness 优化方法进行干净比较；
  • 训练稳定性和 Goodhart effect 仍未解决。

因此，作者认为方向重要，但当前结果仍属于 provisional evidence。

  • 【2026-05-28】【Hexo Labs / Oxford】【arXiv 预印本】SIA: Self Improving AI with Harness & Weight Updates 尝试把 harness 修改和参数更新纳入同一闭环，由 Feedback-Agent 根据执行轨迹选择更新类型。论文是联合优化方向的早期实例，但实验中不同代理的模型能力和基线设置形成较强混杂因素。

3. Future Challenges

3.1 自动写论文不等于自动科学发现

原文认为 AI Scientist 类系统已经证明，专家设计的 harness 可以协调研究流程中的大量操作。但论文生产和科学发现并不相同。

系统可能生成形式完整、语言可信的论文，同时存在：

  • 伪造引用；
  • 实验分数不可复现；
  • 代码与论文描述不一致；
  • 方案在实现中发生漂移；
  • 实验本身很弱；
  • 结论超过证据支持范围。

3.2 四次自主研究实验中的六类失败

Why LLMs Aren’t Scientists Yet 使用极简工具测试模型能否从想法走到论文。工具主要包括：

  • read_file
  • write_file
  • llm_search
  • list_files

每个研究想法拥有独立 workspace，代理可以在其中生成和读取文档。实验覆盖：

  • world models；
  • multi-agent RL；
  • AI safety and alignment。

每个领域提供约 45—50 篇高质量种子文献。人类专家最终选择四个想法进入完整流程，但只有一个被完整执行成论文。

研究总结出六类反复出现的问题：

  1. Bias Toward Training-Data Defaults
    模型倾向使用训练数据中常见但已经过时的库、命令、文件格式和默认假设，而不检查真实仓库与数据。

  2. Implementation Drift Under Execution Pressure
    当原创方法实现困难时，模型逐渐退回更熟悉、更简单的标准方案，最终代码与原始研究想法不再一致。

  3. Memory and Context Degradation
    长项目中若关键信息没有保存为持久产物，模型会忘记此前决定、实验条件和失败原因。

  4. Over-Optimism
    面对噪声或失败结果，模型仍倾向宣布成功，或用临时数值调整让结果看起来合理。

  5. Insufficient Domain Intelligence
    模型缺少研究中的 tacit knowledge，例如实现难度判断、结果合理性判断，以及哪些 baseline 真正重要。

  6. Weak Scientific Taste
    实验可能可以运行，却没有回答最重要的问题；系统难以判断哪个方向值得继续追踪。

  • 【2025-11-20】【OpenAI，联合 Oxford / Cambridge / LLNL 等】【arXiv 预印本】Early Science Acceleration Experiments with GPT-5 记录 GPT-5 在多个真实科研项目中的辅助作用和失败方式。论文观察到模型可能过早宣布发现，通过临时数值修补维持结论，或把噪声解释为突破，原文将其概括为类似 “p-hacking and eureka-ing” 的行为。

  • 【2026-01】【Lossfunk】【arXiv 预印本】Why LLMs Aren’t Scientists Yet: Lessons from Four Autonomous Research Attempts 使用最小 scaffold 运行四项端到端自主研究，仅一项完整完成。论文将失败归因于陈旧默认值、实现漂移、记忆退化、过度乐观、领域知识不足和科学品味薄弱。

3.3 七项核心瓶颈

1. Weak and Fuzzy Evaluators

当前自我改进最成功的任务通常有快速、客观且可重复的评价函数，例如：

  • 单元测试；
  • 编译结果；
  • 数学答案；
  • 游戏得分；
  • 运行速度；
  • benchmark 分数。

但科研价值、创新性、问题选择和长期影响没有同等精确的 verifier。

Research taste 同时涉及：

  • 问题 framing；
  • 实验设计；
  • 对意外结果的判断；
  • 判断哪个失败值得重试；
  • 判断哪个成功其实没有意义。

弱 evaluator 会导致系统优化可测指标，而不是实际目标。

2. Context and Memory Lifecycle

代理越自主，记忆增长越快。系统不仅要“拥有记忆”，还要管理记忆生命周期：

  • 哪些信息进入记忆；
  • 哪些信息过期；
  • 哪些结论互相冲突；
  • 哪些失败应长期保留；
  • 哪些细节只需短期存在；
  • 怎样压缩而不丢失关键因果信息；
  • 怎样从大量历史中检索当前相关经验。

原文进一步推测，context engineering 可能最终成为智能本身的重要组成，而不只是外部软件技巧。人类能够在一生中维护和重组记忆，长期代理也需要类似能力。

3. Negative Results

科学文献偏向发表成功结果，训练数据中的成功案例远多于失败案例。因此模型可能不擅长：

  • 判断何时放弃假设；
  • 承认实验失败；
  • 记录负结果；
  • 区分暂时失败和根本不可行；
  • 避免把失败重新包装为成功。

研究 harness 应让失败尝试容易保存，因为失败可以帮助剪枝搜索空间，避免后续代理重复走相同路径。

4. Diversity Collapse

进化搜索和强化学习都容易利用当前已知高奖励模式，导致种群收敛为同一方案的近似变体。

开放式研究中，这尤其危险，因为真正有价值的路线在早期可能：

  • 得分较低；
  • 不符合当前 evaluator；
  • 需要更长时间才显示价值；
  • 与已有高分方案差异较大。

因此需要多样性维护、新颖性奖励、分支 archive 和不同评价维度。

5. Reward Hacking

自我改进系统会优化它所获得的信号，而不自动理解设计者真正想要的目标。

例如：

  • 奖励来自测试时，代理可能只针对测试过拟合；
  • 奖励来自 judge model 时，代理可能学习讨好该 judge；
  • 奖励来自 benchmark 时，代理可能利用数据或环境漏洞；
  • 若允许修改 verifier，代理可能直接削弱验证条件；
  • 若允许调整预算，代理可能通过增加推理资源而非改进 harness 获得更高分。

因此 evaluator 和 permission control 应位于 harness evolution loop 之外，并结合：

  • held-out tests；
  • trace audits；
  • 只读验证器；
  • 人类审查；
  • 修改范围限制。

6. Long-Term Success

训练 sandbox 中的奖励通常关注单次 rollout 的结果，但真实软件和科研系统需要长期维护。

以编码代理为例，代理可能完成当前 issue，却损害：

  • 可维护性；
  • 模块所有权边界；
  • 迁移成本；
  • 向后兼容性；
  • 技术债；
  • 未来调试难度；
  • 大型团队的协作约定。

这些后果往往不会在短期 benchmark 中立即出现。如何把长期系统健康纳入训练和评价仍是开放问题。

7. The Role of Humans

原文不主张简单移除人类，而是让人类向更高抽象层移动。

人类应在以下位置提供监督和方向：

  • 选择值得研究的问题；
  • 定义评价标准；
  • 设定权限和安全边界；
  • 判断高影响修改；
  • 审查 evaluator 无法可靠判断的结果；
  • 决定何时停止或改变方向。

关键问题不是“是否有人类参与”，而是人类应在什么时间、以什么抽象层级介入。

4. Appendix：Useful Benchmarks

4.1 科研复现与研究代理

  • 【2024-09】【Princeton】【TMLR 2024】CORE-Bench: Fostering the Credibility of Published Research Through a Computational Reproducibility Agent Benchmark 评估代理能否使用论文提供的代码和数据复现已发表结果。基准包含来自计算机科学、社会科学和医学的 90 篇论文，共形成 270 项任务，并设置不同难度以及纯语言和视觉语言版本。原文记录，当时最强设置在最难任务上的准确率仍约为 21%。

  • 【2024-10】【OSU NLP / UW–Madison】【ICLR 2025】ScienceAgentBench: Toward Rigorous Assessment of Language Agents for Data-Driven Scientific Discovery 从数学、化学、生物和地理四个领域的 44 篇同行评审论文提取 102 个科研任务，覆盖数据处理、模型开发、数据分析和可视化。代理需要生成可执行 Python 程序，而不只是自然语言回答。

  • 【2024-10】【OpenAI】【arXiv 预印本】MLE-bench: Evaluating Machine Learning Agents on Machine Learning Engineering 将 75 项 Kaggle 竞赛构造成离线机器学习工程环境，测试数据准备、模型训练、实验管理和预测提交。使用 Kaggle 公开排行榜作为人类基线，并分析推理资源扩展和数据污染问题。论文中最佳设置达到铜牌水平的竞赛比例为 16.9%。

  • 【2024-11】【METR / Redwood Research / Harvard】【ICML 2025】RE-Bench: Evaluating Frontier AI R&D Capabilities of Language Model Agents Against Human Experts 在七个开放式机器学习研究工程环境中比较代理和人类专家。任务包括 kernel 优化、scaling law 实验、embedding 修复和 GPT-2 问答微调。代理在两小时预算下得分可显著高于人类，但人类在八小时和三十二小时预算下具有更好的持续收益。

  • 【2025-02】【Stanford Hazy Research / Princeton】【arXiv 预印本】KernelBench: Can LLMs Write Efficient GPU Kernels? 包含 250 个 PyTorch workload，评价生成 kernel 是否同时正确且快于基线。核心指标 fast_p 表示正确并超过基线速度的 kernel 比例，适合评价编码代理在具有精确执行反馈下的程序优化能力。

  • 【2025-04】【OpenAI】【ICML 2025】PaperBench: Evaluating AI’s Ability to Replicate AI Research 要求代理从零复现 20 篇 ICML 2024 Spotlight 或 Oral 论文，包括理解论文、建立代码库和执行实验。任务被分解为 8,316 个可独立评分的 rubric，并由原论文作者参与制定。基准还包括较轻量的 PaperBench Code-Dev 和用于评价自动评分器的 JudgeEval。

4.2 这些 Benchmark 在原文中的作用

这些 benchmark 分别衡量了自我改进 harness 所需的不同能力：

  • CORE-Bench：能否利用已有代码和数据复现科研结果；
  • ScienceAgentBench：能否完成真实数据驱动科学任务；
  • MLE-bench：能否执行端到端机器学习工程；
  • RE-Bench：能否在开放式研发环境中与人类专家竞争；
  • KernelBench：能否在明确 verifier 下优化高性能程序；
  • PaperBench：能否从论文描述重建完整研究产物。

它们共同说明，评价 harness 不能只看最终自然语言答案，还需要检查：

  • 代码；
  • 执行结果；
  • 实验产物；
  • 资源使用；
  • 可复现性；
  • 长时程表现；
  • 与人类专家的比较。

5. 原文整体方法脉络总结

原文所描述的 harness 自我改进路线可以概括为五层。

第一层：Workflow

先建立稳定的 Plan → Execute → Observe/Test → Improve 循环，让模型能够持续行动，而不是一次性回答。

第二层：Persistent State

把日志、代码、轨迹和实验结果保存到文件系统，避免长期任务完全依赖上下文窗口。

第三层：Structured Context and Agent Organization

使用结构化 playbook、记忆维护、子代理和后台任务，提高长流程的信息密度和并行能力。

第四层：Harness as Code

将 prompt、工具、memory、workflow、permissions 和 sub-agent configuration 统一表示为可执行代码，使整个系统成为可搜索和可修改对象。

第五层：Optimizer Self-Improvement

进一步优化：

  • 生成 harness 修改的 proposer；
  • 选择候选的搜索算法；
  • 维护种群的进化机制；
  • 决定 context 如何更新的 skill；
  • 决定更新 harness 还是权重的 feedback policy。

最终优化对象从“答案”转向“产生和改进答案的机器”。

但原文始终保留一个限制条件：

Harness 可以放大、组织和持久化基础模型已有的智能，却不能保证弱模型通过递归结构自动变强。成功的自我改进同时需要：

  • 足够强的基础模型；
  • 可执行且可检查的系统表示；
  • 高质量 evaluator；
  • 可追踪的失败证据；
  • 严格的权限边界；
  • held-out validation；
  • 多样性维护；
  • 对负结果和长期影响的建模；
  • 在关键抽象层级上的人类监督。
